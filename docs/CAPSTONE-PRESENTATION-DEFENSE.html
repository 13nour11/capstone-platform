The Order Saga: Choreography & Compensation Flow

Two Paths: Synchronous Fail-Fast (Feign) and Asynchronous Eventual Consistency (Kafka)
Slide 03 / 20
✅ Happy Path Flow (Order Placement to Completion)
  1. POST /api/v1/orders + Bearer JWT arrives at api-gateway:8080.
  2. Stock Pre-Check: order-service calls inventory-service:8084 via OpenFeign (outside DB transaction).
  3. Atomic Insert: OrderPersistenceService persists Order (PENDING) and OutboxEvent (OrderPlaced) in 1 ACID transaction.
  4. Kafka Publish: Scheduled Outbox publisher transmits OrderPlaced to order-events.
  5. Stock Reservation: inventory-service consumes event, executes pessimistic lock, updates stock, writes InventoryReserved to outbox.
  6. Payment Charge: payment-service consumes InventoryReserved, checks idempotency key, charges, writes PaymentCompleted.
  7. Order Confirmation: order-service consumes PaymentCompleted, updates status to CONFIRMED. Customer is notified (FR-11).
⚠️ Compensation & Failure Rollback Paths
  1. Stock Shortage (Step 2): Feign stock check fails fast; request rejected with 422/400 before any DB lock or message is created!
  2. Payment Declined / Failure (Step 6): payment-service emits PaymentFailed event to payment-events.
  3. Stock Rollback: inventory-service consumes PaymentFailed and atomically restores the reserved stock quantity.
  4. Order Cancellation: order-service consumes PaymentFailed and transitions order to CANCELLED.
  5. Customer Notice: notification-service delivers a cancellation notice to the customer.
  6. Poison Pill Defense: Malformed Kafka events trigger exponential retries before routing to .DLT.

Examiner Q&A Defense Strategy

Architectural Defense for Dr. Baladoh's Tough Questions
Slide 12 / 20
Q1: "Why Feign stock check if you have an asynchronous Saga?"

Answer: "Hybrid fail-fast pattern. Feign checks stock outside the DB transaction. This eliminates 95% of wasted database commits and Kafka broker traffic for obviously out-of-stock items, while the asynchronous Saga provides true eventual consistency and handles concurrent race conditions via pessimistic DB locks."

Q2: "What happens if a service crashes after committing DB but before sending Kafka?"

Answer: "This is why we built the Transactional Outbox pattern. The message is never sent directly inside the request thread. It is written to outbox_event in the same ACID transaction. An independent scheduled poller sends it with synchronous Kafka ACKs. Even on crash, the event persists and is published upon restart. Zero message loss."

Q3: "How do you guarantee idempotency against Kafka duplicates?"

Answer: "Every consumer checks an idempotent_event table with a unique constraint on (event_id, consumer_group). If Kafka re-delivers a message, the database throws DataIntegrityViolationException, which our listener catches and cleanly ACKs without re-executing business logic."

Q4: "Why did you separate OrderPersistenceService from OrderServiceImpl?"

Answer: "In Spring, @Transactional operates through dynamic AOP proxies. If a method in OrderServiceImpl calls another transactional method in the same class (this.method()), Spring bypasses the proxy and no transaction is opened! Delegating to a separate bean ensures Spring's proxy intercepts the call and maintains atomic transaction boundaries while keeping Feign I/O outside."
