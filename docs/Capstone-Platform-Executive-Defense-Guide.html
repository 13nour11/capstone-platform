2. Choreographed Saga & Core Invariants

Two Paths: Synchronous Fail-Fast vs. Asynchronous Consistency

The architecture explicitly separates the synchronous path (Order → Inventory via OpenFeign) from the asynchronous path (Choreographed Saga via Kafka). The caller receives an immediate answer ("Can I accept this order right now?") while the long-lived business transaction completes reliably in the background.

1. Happy Path Order Flow:
  1. Client submits POST /api/v1/orders with a valid Bearer JWT.
  2. OpenFeign Pre-Check: order-service queries inventory-service:8084/api/v1/inventory/check outside the database transaction.
  3. Atomic Database Write: OrderPersistenceService persists Order (PENDING) and OutboxEvent (OrderPlaced) in a single ACID transaction.
  4. Kafka Publish: Scheduled publisher sends OrderPlaced to Kafka topic order-events.
  5. Stock Reservation: inventory-service consumes event, executes PESSIMISTIC_WRITE lock, deducts available stock, and emits InventoryReserved.
  6. Payment Processing: payment-service consumes InventoryReserved, checks idempotency key, charges account, and emits PaymentCompleted.
  7. Order Confirmation: order-service consumes PaymentCompleted and sets status to CONFIRMED. notification-service dispatches notification.
2. Compensation & Rollback Paths:
  • Stock Shortage (Pre-Check): Order is rejected immediately with 422/400 before any database record or outbox event is created.
  • Payment Declined / System Failure: payment-service publishes PaymentFailed. In response:
    • inventory-service consumes PaymentFailed and atomically restores reserved stock back to available_quantity.
    • order-service consumes PaymentFailed and transitions order status to CANCELLED.
    • notification-service dispatches order cancellation notice to the customer.

Core Invariants Defended in Code

  • Zero Network I/O in DB Transactions: OpenFeign stock checks are completed before opening @Transactional in OrderPersistenceService, preventing database pool exhaustion.
  • Transactional Outbox Pattern: Business entities and events are saved in the same database transaction. Publishers use synchronous ACK (.get(5, SECONDS)) and halt batch processing on error to guarantee sequential delivery.
  • Idempotency: Consumers deduplicate messages using processed_event unique database constraints, catching DataIntegrityViolationException to safely acknowledge duplicates.
  • Distributed Tracing (W3C traceparent): Outbox tables store active W3C traceparent headers (`00---01`), ensuring end-to-end trace correlation in Zipkin across HTTP and Kafka.

5. Examiner Q&A Defense Cheat-Sheet

Q1: Why use an OpenFeign stock pre-check if you already have an asynchronous Saga?
"It is a hybrid fail-fast design. The OpenFeign check runs outside the database transaction. It filters out 95% of invalid orders (out-of-stock items) immediately without creating database records or publishing Kafka events. The asynchronous Saga then guarantees eventual consistency and handles concurrent race conditions via pessimistic database locks."
Q2: What happens if a microservice crashes right after committing to the database but before sending the Kafka event?
"This is the classic dual-write hazard. We resolved it using the Transactional Outbox pattern. The service never calls Kafka inside the request thread. Instead, the entity and the outbox event are saved in the same ACID database transaction. An independent scheduled poller transmits the event with synchronous broker ACKs (`.get(5, SECONDS)`). If the container crashes, the event remains in the database and is published upon restart. Zero message loss."
Q3: How do you prevent duplicate charges if Kafka delivers the same event twice?
"Every consumer is idempotent. We maintain a `processed_event` table with a unique constraint on `(event_id, consumer_group)`. When an event arrives, we record its ID inside the database transaction. If it is redelivered, the database throws `DataIntegrityViolationException`, which our handler catches and cleanly acknowledges without re-executing business logic."
Q4: Why did you separate OrderPersistenceService from OrderServiceImpl?
"Spring's `@Transactional` works via dynamic AOP proxies. If a method in `OrderServiceImpl` calls another transactional method in the same class (`this.method()`), Spring bypasses the proxy and no transaction is opened! By delegating to `OrderPersistenceService`, we ensure Spring's proxy intercepts the call and maintains atomic transaction boundaries while keeping Feign I/O outside the transaction."
